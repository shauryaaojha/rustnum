Rust-Native ML Stack

Can every layer of machine learning, from GPU kernels to a deployed model, be written in Rust with no C or C++ of our own? This page maps each layer, what exists today, how mature it is, the measured evidence, and what our project should build next. Our first library, rustnum, is a NumPy port in pure Rust (v0.1: 1398 tests, 93/93 NumPy parity cases).

25 searchesRead in full: Are We Learning Yet, NVIDIA's CUDA Rust post, Burn 0.20 release notes, crates.io registry dataRevision 2 applies two external reviews

Decision. Build the full stack's missing top (task API, classical ML on CPU and GPU, deployment, Python bindings) and make rustnum fast, on top of Burn/CubeCL and Polars for tensors, GPU kernels and data. All phases stay in scope; they run in parallel with our agent fleet, ordered only by dependency.

What "pure Rust" means here: every line of code we write or depend on is Rust. Vendor GPU drivers and the compiler backend (LLVM) sit below that line and are listed separately in L0.

Short answer

Yes for one machine, not yet at cluster scale

Ready Rust can own this today

  • Inference on CPU, GPU, edge and in the browser
  • Data: dataframes, Arrow, query engines, columnar formats
  • Tokenizers, model formats, vector search

Partial Usable, with gaps

  • Single-machine training of small and mid-size deep models (Burn)
  • GPU kernel languages: CubeCL's matmul was within 2% of LibTorch's cuBLAS-backed matmul in Burn's own benchmark; no independent cross-GPU test found
  • Classical ML toolkits, gradient boosting, AutoML
  • Statistics, time series, Bayesian modelling

Early Not ready yet

  • Training across many nodes (NCCL has no Rust replacement)
  • Fine-tuning and LoRA, reinforcement learning
  • Autodiff in the compiler (std::autodiff is nightly only)
  • Plotting with seaborn-level statistics

This matches the community map at Are We Learning Yet, which calls Rust "a credible choice for inference and for training on a single machine," but not for "research or training at scale." Every "Early" item above is a place we can build.

L9
Task API and AutoMLGap linfa, smartcore 0.6.16, automl (smartcore-based), hyperopt-rsevidence
  • Rust has algorithms and some model comparison: the automl crate compares smartcore classifiers with cross-validation, and hyperopt-rs is an Optuna-shaped tuner.
  • What does not exist is a widely adopted workflow that spans preprocessing, model search, tuning, classical models and deep models behind one call, with a deployable output.
  • PerpetualBooster (pure Rust) replaces tuning with one "budget" knob: same MSE as Optuna + LightGBM on California Housing at 42–59x less wall time self-reported
L8
Deploy and serveReady tract, candle, mistral.rs, axum, WASM + WebGPU, no_stdevidence
  • tract (Sonos): pure-Rust ONNX/NNEF inference with no C++ dependencies, runs in WASM; FOSDEM 2026 says it is deployed "on millions of devices" self-reported
  • Kyutai Moshi moved from PyTorch to a Rust/candle inference stack; the talk claims 500,000 sessions on L4 GPU clusters self-reported
  • mistral.rs: LLM serving with GGML, GPTQ, FP8 and in-situ quantization; claims to beat llama.cpp on Gemma 4 prefill self-reported. Its older public table is mixed (faster on RTX 6000 and A10, slower on A100 and CPU).
  • WebGPU ships in Chrome and Edge (since 113), Firefox on Windows (since 141) and Apple-silicon Macs (147), and Safari 26. Storage buffers per binding are often capped at 128–256 MB.
  • The Rust advantage: one codebase and one model file for training and serving, compiled per target (native, WASM, no_std), with no Python runtime to ship. Python can reach production through libtorch or ONNX Runtime, but only after an export step and a second runtime.
L7
LLMs, retrieval, agentsReady tokenizers, safetensors, tiktoken-rs, Qdrant, tantivy, LanceDB, Meilisearch, rmcpevidence
  • "Every AutoTokenizer call in Python runs Rust" (Are We Learning Yet). Hugging Face reports under 20 s to tokenize 1 GB on a server CPU self-reported
  • Vector search and full-text search are Rust-first. MCP has a Tier 1 Rust SDK.
  • Fine-tuning, LoRA and post-training are early.
L6
Deep-learning trainingPartial burn 0.22.1 (Oct 2026), burn-collective, rwrd (RL on burn)evidence
  • Burn trains on CUDA, ROCm, Metal, Vulkan, WebGPU, CPU, WASM and no_std from one model definition. Distributed data parallel arrived in 0.19 with its own gradient-sync crate.
  • Burn 0.21 claims up to 8x lower framework overhead, mostly visible on small models self-reported. 0.22 picks the device at run time and was a breaking migration (MSRV 1.95), per a 2026 review.
  • Training across many nodes is missing: for NVIDIA clusters "NCCL. No real alternative" (2026 collectives guide).
  • Reinforcement learning: rwrd 0.4 (Mar 2026) follows Stable-Baselines3 on burn.
L5
Classical ML and statisticsPartial linfa 0.8.1, smartcore 0.6.16, perpetualevidence
  • Clustering, dimensionality reduction, nearest neighbours and optimization are complete; toolkits, boosting, statistics, Bayesian and time series are partial (Are We Learning Yet).
  • smartcore is active: 0.6.16 released 12 Oct 2026 (crates.io). linfa 0.8.1 builds on ndarray.
  • None of them run classical models on a GPU. XGBoost and LightGBM do, in C++.
L4
Data and loadingReady polars, arrow-rs, datafusion, lance, parquetevidence
  • Dataframes, query engines and columnar formats are complete. Arrow 23 (Jan 2026) adds experimental zero-copy sharing between processes.
  • Lance is a Rust columnar format for ML with fast random access, vector indexes and versioning.
  • Gap: a training data loader (shuffle, shard, prefetch to GPU, augment) like PyTorch's DataLoader is only partial.
L3
Tensors, autodiff, graph compilersPartial burn + CubeCL fusion, candle, luminal, std::autodiff (nightly)evidence
  • Burn: tensors with autodiff and kernel fusion across backends.
  • candle: inference-first. About 80% Rust; its CUDA and Metal kernels are not Rust, and FlashAttention v2 needs CUTLASS.
  • luminal: search-based compiler (equality saturation + cost model) that aims to discover kernels like FlashAttention automatically; CUDA and Metal in production.
  • std::autodiff: forward and reverse mode in rustc via Enzyme, nightly only, needs lto = "fat".
  • Excluded by our rule: tch (libtorch bindings) and ort (ONNX Runtime bindings) are C++ underneath.
L2
CPU numericsReady rustnum (ours), ndarray, nalgebra, faer, matrixmultiply, gemmkit, wideevidence
  • faer's benchmark: parallel faer multiplies 768×768 f64 in about 2.9 ms against Eigen 3.2 ms and OpenBLAS 3.6 ms; single-threaded it trails self-reported
  • gemmkit dispatches AVX-512 (VNNI int8, BF16), NEON and wasm simd128 at run time.
  • rustnum today: wins on sums, behind on BLAS/LAPACK-class kernels (see the evidence table). faer shows these gaps are about our implementation, not about Rust.
L1
GPU kernel languagesPartial CubeCL / CubeK, NVIDIA cutile-rs and cuda-oxide, rust-gpu, rust-cuda, wgpuevidence
  • CubeCL (burn): write a kernel once in Rust, run it on CUDA, ROCm, Metal, Vulkan, WebGPU and CPU. Burn 0.20 matmul 4096²: 639 µs vs LibTorch 627 µs (2% slower) self-reported
  • NVIDIA CUDA Rust (Sept 2026): cutile-rs runs tile kernels on stable Rust with CUDA 13.3; cuda-oxide is a rustc backend emitting PTX on a pinned nightly. NVIDIA: "Both projects are early-stage and neither is production-ready."
  • rust-gpu (SPIR-V): "not yet production-ready". Its maintainer recommends cuda-oxide over rust-cuda for anything new.
  • Kernel speed, framework speed and production readiness are separate claims; only the first has evidence here, and only from the projects themselves.
L0
Drivers and toolchainNot Rust NVIDIA driver and CUDA runtime, ROCm, Mesa, Metal, LLVM inside rustcevidence
  • GPU drivers are C/C++: closed for NVIDIA and Apple, open source for AMD ROCm and Mesa. The PTX JIT runs inside NVIDIA's driver.
  • rustc's default code generator is LLVM (C++). Cranelift is a Rust alternative for CPU code that generates slower code today.
  • Our rule stops at this line: no C/C++ source in our repos or our dependencies; drivers and the compiler backend are documented, not rewritten.

The pattern: Rust wins where work can be fused or framework overhead skipped, and where we wrote a good kernel (pairwise sum). It loses where our first implementation is still simple (Jacobi SVD, unblocked LU, scalar exp) against LAPACK, OpenBLAS and NumPy's SIMD loops. The Burn wins are against eager LibTorch on CPU, the case where eager frameworks are weakest; on plain sums LibTorch is level. faer's results show the LAPACK-class gap can be closed in Rust.

Why Rust, concretely

What a Rust-native stack does better, and what it does not yet

Structural advantages

  • One language from kernel to API. Python ML is Python over C++ over CUDA. In Rust the model, the kernels (CubeCL, cutile-rs) and the server can be one codebase, one debugger, one build system.
  • One codebase and model file for train and serve. Compiled per target, with no Python runtime, no export step and no GIL. Python's route is libtorch or ONNX Runtime after export.
  • One kernel source, many GPU vendors. CubeCL targets NVIDIA, AMD, Apple, Vulkan, WebGPU and CPU. Triton, XLA and SYCL also target several vendors; CubeCL is the one that also reaches the browser and no_std.
  • Fusion without a separate compile step. Burn fuses lazily by default; PyTorch fuses through torch.compile.
  • Safe concurrency. Data loading, augmentation and serving in parallel threads, with data races caught at compile time.

Where Python is still ahead

  • Research speed. New papers ship PyTorch code; notebooks and plotting are weaker in Rust.
  • Pretrained models. Rust loads safetensors but has fewer model implementations.
  • Multi-node training. No NCCL replacement yet.
  • LAPACK-class kernels in our code. Our SVD is 16x and inv 6.3x behind.
  • Compile times and the learning curve for researchers used to Python.
Recommendation for ML in Rust

Build the missing top, make the bottom fast, reuse what is proven

Writing our own GPU compiler would duplicate CubeCL, so we reuse it and contribute kernels to it. Everything else that is empty or partial is ours to build: the task layer, classical ML on CPU and GPU, deployment, a GPU data loader, Python bindings, and a fast rustnum.

Phases

Roadmap with exit criteria

Phases A–D can run at the same time in separate worktrees, as rustnum was built. The order below shows dependencies, not a reduced scope.

Phase AMedium

rustnum performance

faer as the decomposition backend (LU, QR, SVD, eig), cache-blocked axis reductions and transposes, SIMD element-wise math, parallel sort.

Exit: every benchmark in the README within 1.5x of NumPy + OpenBLAS at equal thread counts, parity still 93/93.

Phase BLarge

Tabular task layer

Classifier, Regressor and Clusterer traits; linear and logistic models, trees, random forest, histogram gradient boosting, kNN, SVM, preprocessing, metrics, cross-validation and model search, with auto().

Exit: datasets, metrics, seeds and tolerances fixed before running. Classification: ROC-AUC and macro-F1 within 0.01 absolute of scikit-learn; regression: RMSE within 2% relative; clustering: ARI within 0.02, each on 10 public datasets with 5-fold CV. Training time and peak memory reported next to scikit-learn and LightGBM.

Phase CSmall

Deploy and Python bindings

Versioned model file, model.save() and load(), native, WASM and no_std builds, a PyO3 wheel.

Exit: predictions agree across Windows, Linux and Chrome (WASM) within 1e-6 relative for f64; the wheel installs with pip and passes the same parity tests.

Phase DLarge

Classical ML on GPU

CubeCL kernels for histograms, split finding and distance matrices so boosting and kNN run on NVIDIA, AMD, Apple and WebGPU, chunked to stay under browser buffer limits.

Exit: GPU boosting training time within 2x of XGBoost GPU on a 1M-row dataset at matched depth, rounds and bins, with equal-or-better validation AUC.

Phase ELarge

Deep models behind the same API

MLP, CNN and Transformers via Burn, searched by Classifier::auto next to the classical models; GPU DataLoader.

Exit: one image and one text classification task solved end to end with one call, accuracy reported against a PyTorch baseline.

Phase FLarge

The early layers

LoRA fine-tuning, reinforcement learning, seaborn-style statistical plotting, and a Rust collective-communication layer for multi-node training.

Exit per item, defined when the phase starts.
